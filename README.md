# BOT_CALENDAR — платформа записи: Telegram + Google Calendar + AI

Система онлайн-записи к специалисту под ключ: клиент записывается в
Telegram-боте — кнопками или просто фразой, администратор ведёт всё в
веб-панели, событие появляется в Google Calendar сотрудника. Поставляется
заказчику вместе с ключами — свой бот, свой проект Google, свой сервер.

> **Состояние на 11 сентября 2026.** Всё, что перечислено в «Что работает»,
> сделано и проверено тестами (236). **Демо-стенд развёрнут:**
> https://calendar.138-124-63-48.nip.io/admin. Идёт этап 8 — демо на данных
> компании ВайбМайнд: исключения расписания, профиль компании, база знаний,
> загрузка «пакета компании» и ИИ-консультант в диалоге готовы; полная админка и
> права сотрудников — в работе. Подробности в [ROADMAP.md](ROADMAP.md).

## Что работает

**Клиент в Telegram-боте**
Записывается в пять шагов: услуга → специалист → день в календаре → свободное
время → подтверждение. Смотрит свои записи, переносит и отменяет их сам.

**ИИ-консультант в диалоге**
Клиент пишет своими словами — «какие у вас услуги?», «сколько стоит обучение на
40 человек?», «запишите к Евгению после обеда». Консультант отвечает по базе
знаний компании, помнит разговор, сам находит свободное время и показывает
карточку с кнопкой «Записаться». Записывает только нажатие кнопки: модель
записей не создаёт. OpenRouter, модель Qwen; без ключа бот работает кнопками.

**Данные компании одним файлом**
Профиль, база знаний, услуги, сотрудники и расписания — в «пакете компании»
(JSON). `python -m app.cli import-company seed/vibemind.json` загружает демо
ВайбМайнд: сначала показывает, что изменится, записи и клиентов не трогает,
лишнее уходит в архив. «Информация» и приветствие бота берутся из профиля.

**Выходные и исключения**
Поверх недельного расписания — выходной или отпуск на диапазон дат, закрытое
время и дополнительное окно (например, в субботу). Календарь бота показывает
только дни, когда специалист принимает.

**Напоминания**
За сутки и за час до визита клиент получает сообщение с кнопками «Перенести» и
«Отменить». Интервалы настраиваются в админке, каждое напоминание уходит один раз.

**Администратор в веб-панели**
Сотрудники и их права, услуги, клиенты, расписание с перерывами, записи,
подключение календарей, настройки напоминаний, журнал действий. Четыре роли и
десять отдельных прав, меню показывает только доступное.

**Компания, база знаний, диалоги**
В разделе «Компания» — профиль, от имени которого говорит бот, настройки
ИИ-консультанта (модель, лимиты, память), скачивание и загрузка пакета компании
с предпросмотром изменений и кнопка, которая переносит имя и описание в профиль
бота в Telegram. «База знаний» — статьи, из которых консультант берёт факты.
«Диалоги» — переписка клиентов с консультантом и записи, сделанные через него.

**Правка всего и архив**
Карточка записи — любое поле: клиент, специалист, услуга, дата, время, заметка,
статус; при смене специалиста событие переезжает в его календарь. Карточка
клиента — его записи и диалог; по запросу на удаление данных клиент удаляется
вместе с записями и перепиской. Услуги — цена суммой, «бесплатно» или «по
договорённости», кто проводит. Сотрудники — «о специалисте», услуги, логин и
роль. Ушедших сотрудников и старые услуги можно убрать в архив: история
сохраняется, из бота и списков они пропадают. Удалить насовсем можно то, у чего
нет записей. «Пользователи» — логины, роли и права; удалить себя или последнего
администратора нельзя.

**Google Calendar**
У каждого сотрудника свой календарь, подключается кнопкой через OAuth. Запись
создаёт событие, перенос двигает то же самое событие, отмена его удаляет.
Занятость из Google убирает слоты из выдачи — личные встречи сотрудника клиенту
не предлагаются. Правки, сделанные сотрудником прямо в Google, возвращаются
в базу раз в 10 минут.

**Двойная бронь исключена**
Redis-lock на сотрудника плюс проверка пересечений в той же транзакции, что и
запись. Два клиента, нажавшие один слот одновременно, получат разный результат:
один запись, второй — предложение выбрать другое время.

**Развёртывание в Docker**
Один образ для API и бота, подготовка чистого Ubuntu одним скриптом, повторный
деплой одной командой. Наружу открыт только nginx с сертификатом, база и Redis
недоступны из интернета.

## Чего ещё нет

- Права сотрудника «только своё», выходные и дополнительные окна в интерфейсе
  админки (сейчас — через пакет компании), уведомления сотрудникам в Telegram,
  шаг сетки и горизонт записи в настройках — этап 8E.
- Мастер первичной настройки `/setup` — ключи пока вписываются в `.env` руками.
- Вебхук вместо long polling и мгновенные правки из Google вместо опроса.

Сроки и состав — в [ROADMAP.md](ROADMAP.md).

## Как это устроено

```
Клиент → Telegram-бот ──┬─ кнопки ─────────────┐
                        └─ фраза → AI-разбор ──┤
                                               ├→ booking_flow → PostgreSQL (+ Redis lock)
Админ  → Админ-панель ─────────────────────────┘        │
                                                        └→ google_event_id ↔ Google Calendar

Планировщик в процессе API:
  синхронизация Google → база — раз в 10 минут
  напоминания клиентам        — раз в 5 минут
```

Три правила, из которых следует почти всё остальное:

**Источник истины — PostgreSQL, а не Google Calendar.** Календарь — витрина для
сотрудника; связывает их `booking.google_event_id`. Поэтому сбой Google не
отменяет бронь: запись коммитится, ошибка уходит в аудит, администратор видит
«запись создана, но событие в календаре не создано».

**Единая точка бронирования — `app/services/booking_flow.py`.** Админка, кнопки
бота и AI ходят через неё, поэтому правила записи не расходятся между
интерфейсами: добавленная там проверка немедленно действует везде.

**ИИ советует и предлагает, но не записывает.** У модели три инструмента: найти
свободное время, показать карточку записи, показать записи клиента. Запись
создаёт только нажатие «Записаться» — через тот же `booking_flow`, что и кнопки.
Записать без подтверждения, отменить чужое или обойти защиту от двойной брони
ИИ не может: у него нет такого пути.

Подробнее — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Развёртывание: действия владельца

### До развёртывания · сделано

**1. Положить ключ деплоя на сервер — один раз.** Двойной клик по файлу
**`Подключить сервер.bat`** в папке проекта. Откроется окно, сервер один раз
спросит пароль root: наберите его (символы не отображаются) и нажмите Enter. В
конце окно само проверит вход без пароля и напишет «ГОТОВО! Ключ работает».

Пароль вводите вы: ни скрипт, ни разработчик его не видят и не хранят. Так же
устроено в проекте ВайбМайнд — там пароль root нужен только при первичной
установке ключа, дальше `Деплой.bat` ходит по ключу.

Если удобнее терминал — то же самое в Git Bash из папки проекта:

```bash
bash scripts/add_deploy_key.sh
```

Самопроверка — эта команда должна напечатать `ok` **без запроса пароля**:

```powershell
ssh -i ~/.ssh/bot_calendar_deploy root@138.124.63.48 "echo ok"
```

Спрашивает пароль — ключ не добавился, повторите шаг 1. Лишних попыток лучше не
делать: хостинг временно блокирует SSH после серии неудачных входов.

Если в окне `Connection closed by 138.124.63.48 port 22`, а пароль даже не
спросили, — это та самая блокировка, пароль тут ни при чём. Подождите 15 минут,
ничего не запуская, и повторите один раз. Быстрее — подключить компьютер к
раздаче интернета с телефона: у неё другой IP, и блокировка на него не
распространяется.

**2. Разрешить сертификат.** Для HTTPS certbot принимает условия Let's Encrypt
от имени владельца сервера. Email не регистрируется, продление автоматическое.
Нужно явное «согласен».

**3. Google Cloud.** Credentials → ваш OAuth-клиент → Authorized redirect URIs →
добавить:

```
https://calendar.138-124-63-48.nip.io/oauth/google/callback
```

### Что делает разработчик · сделано

Подготовка сервера (Docker, nginx, swap, файрвол) → `.env` для сервера →
сертификат → остановка локального бота (два бота на одном токене Telegram не
пустит) → запуск контейнеров → проверка `/health` снаружи. Около 15 минут.

Проверка 10.09: `https://calendar.138-124-63-48.nip.io/health` — все поля `true`,
HTTP перенаправляется на HTTPS, бот принимает `/start` с сервера.

### После развёртывания

**4. Создать администратора.** Пароль вводите вы, у разработчика его не будет.
Команда работает и в cmd, и в PowerShell; спросит логин, пароль (от 8 символов)
и повтор пароля. Если перед этим спросила пароль root — ключ не нашёлся, проверьте
путь `~/.ssh/bot_calendar_deploy`:

```powershell
ssh -t -i ~/.ssh/bot_calendar_deploy root@138.124.63.48 "cd /opt/bot-calendar && docker compose -f docker-compose.prod.yml exec api python -m app.cli create-admin"
```

**5. Наполнить админку** на `https://calendar.138-124-63-48.nip.io/admin`:
сотрудник → услуга → расписание → «Календари» → «Подключить Google» → рабочий
календарь. Порядок — в [docs/ADMIN.md](docs/ADMIN.md).

**6. Проверить в боте:** запись кнопками; фраза «хочу на консультацию завтра
после обеда»; «Мои записи» → перенос и отмена. Событие должно появляться и
исчезать в Google Calendar.

## Быстрый старт (разработка)

```bash
# 1. Инфраструктура (PostgreSQL + Redis)
docker compose -f docker-compose.dev.yml --env-file .env up -d

# 2. Зависимости
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 3. Конфигурация
cp .env.example .env   # и заполнить своими ключами

# 4. Миграции БД
.venv\Scripts\alembic upgrade head

# 5. Первый администратор
.venv\Scripts\python -m app.cli create-admin

# 6. Два процесса: API с админкой и бот
.venv\Scripts\uvicorn app.main:app --reload
.venv\Scripts\python -m app.bot.main
```

| Адрес | Что там |
|---|---|
| http://localhost:8000/admin | Админ-панель |
| http://localhost:8000/health | Состояние: база, Redis, планировщик, Google, AI |
| http://localhost:8000/api/docs | Swagger (выключается в production) |

## Безопасность

- Секреты только в `.env`, в git он не попадает. У заказчика — свои ключи,
  ключи разработчика при передаче отзываются ([docs/TRANSFER.md](docs/TRANSFER.md)).
- `.env` для сервера собирается скриптом, который не печатает значений, а
  секреты приложения генерирует заново.
- Деплой ходит на сервер по отдельному ключу; пароль root скриптам не нужен.
- Наружу открыт только nginx; PostgreSQL и Redis из интернета недоступны, API
  слушает только локальный адрес.
- Refresh-токены Google шифруются (Fernet) перед записью в БД. Сотрудник их не
  видит, клиент-секрет ему не нужен.
- Пароли — bcrypt. Сессия администратора — JWT в HttpOnly-cookie, в production
  только по HTTPS.
- Клиент бота видит и меняет только свои записи — владелец проверяется на
  каждой операции, не только при показе списка.
- В AI-модель уходят только текст сообщения и справочники — без имени, телефона
  и Telegram ID клиента. Не больше 20 разборов в час на клиента.
- Каждое изменение попадает в журнал `/admin/audit`: кто, что, когда.
