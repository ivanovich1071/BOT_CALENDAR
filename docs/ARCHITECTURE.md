# Устройство системы

Для того, кто будет её дорабатывать. Не пересказ кода, а решения и их причины:
почему сделано так, а не иначе, и что сломается, если переделать наоборот.

---

## Два процесса, одна база

```
┌──────────────────────────┐        ┌──────────────────────────┐
│  uvicorn app.main:app    │        │  python -m app.bot.main  │
│  ────────────────────    │        │  ──────────────────────  │
│  Админка (Jinja2+HTMX)   │        │  Telegram-бот (aiogram)  │
│  OAuth callback Google   │        │  long polling            │
│  APScheduler:            │        │                          │
│    Google → БД, 10 мин   │        │                          │
└───────────┬──────────────┘        └───────────┬──────────────┘
            │                                   │
            └──────────────┬────────────────────┘
                           ▼
              app/services/booking_flow.py
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   PostgreSQL          Redis-lock       Google Calendar
  (источник истины)  (двойная бронь)     (событие)
```

Бот — отдельный процесс, потому что long polling блокирует свой event loop, а
падение бота не должно ронять админку. Общего кода у них нет вообще, кроме
`booking_flow` и слоя данных — и это намеренно.

---

## Решение 1. PostgreSQL — источник истины, Google — витрина

Календарь не хранит бизнес-данных: у события в Google нет ни статуса записи, ни
клиента, ни услуги, ни истории. Он нужен сотруднику, чтобы видеть свой день в
привычном интерфейсе и на телефоне.

Связь — `booking.google_event_id`. Одно поле, из которого следует:

- **перенос двигает то же событие,** а не создаёт второе;
- **отмена удаляет именно его;**
- **дублей в календаре не бывает** — id известен, правка идёт по нему.

Обратное направление обеспечивает синхронизация: сотрудник подвинул событие
руками в Google → задача планировщика читает изменения по `syncToken` и правит
`bookings.start_at`. То есть Google может менять время, но не может создать
запись — записи рождаются только в системе.

### Из этого же следует: сбой Google не отменяет бронь

`booking_flow` коммитит запись в PostgreSQL, а потом пробует записать событие.
Не получилось — бронь всё равно есть, ошибка уходит в `audit_logs`
(действие `google.push_failed`), а вызывающему возвращается признак:

| Значение | Что произошло |
|---|---|
| `None` | Календарь не подключён — события и не ожидалось |
| `True` | Событие записано |
| `False` | Google не ответил, запись живёт только в БД |

Админка на `False` показывает «Запись создана, но событие в календаре не
создано». Клиенту в боте про Google не говорится ничего — ему это не нужно,
запись у него есть.

---

## Решение 2. Единая точка бронирования

`app/services/booking_flow.py` — единственный способ создать, перенести или
отменить запись. Ни админка, ни бот не ходят в `booking_service` напрямую.

| Функция | Что делает |
|---|---|
| `available_slots(db, employee_id, service_id, day, exclude_booking_id)` | Расписание − перерыв − брони − занятость Google |
| `create(db, ...)` | Проверка → запись в БД → событие в Google → аудит |
| `reschedule(db, booking_id, new_start, actor)` | То же, но правка существующего события |
| `cancel(db, booking_id, actor)` | Статус «отменена» + удаление события |
| `set_status(db, booking_id, status, actor)` | Завершена / неявка, календарь не трогается |

Причина: бот появился через этап после админки. Если бы правила жили в
хендлерах админки, бот продублировал бы их целиком — и первое же расхождение
(скажем, добавили проверку «нельзя записаться менее чем за час») дало бы две
разные системы записи внутри одного продукта.

Проверить это легко: `admin/routes/bookings.py` не импортирует
`calendar_service` вообще.

### Тонкость: своё событие не должно мешать переносу

При переносе внутри того же дня событие переносимой записи лежит в Google и
закрывает соседние слоты — бронь конфликтует сама с собой. `_without_own_event`
убирает его из занятости по совпадению границ.

## Решение 3. Защита от двойной брони

Два уровня, и оба нужны:

1. **Redis-lock на сотрудника** — отсекает гонку между процессами (админ и
   клиент нажали одновременно). Блокировка короткая, только на время проверки
   и вставки.
2. **Проверка пересечений в той же транзакции** — работает, даже если Redis
   лёг. Redis ускоряет и делает отказ понятным, но не является условием
   корректности.

Убрать второй уровень — недоступность Redis откроет окно для двойной брони.
Убрать первый — двойной брони не будет, но второй клиент получит не «выберите
другое время», а ошибку транзакции.

## Решение 4. Планировщик внутри процесса API

APScheduler запускается в `lifespan` FastAPI, отдельного сервиса нет: система
эксплуатируется в одиночку, а лишний процесс — лишняя точка отказа и лишний
пункт в инструкции по установке.

От дублирования при нескольких воркерах uvicorn защищает Redis-lock
`scheduler:google_sync`: задачу выполняет тот, кто первым её взял. Redis
недоступен — задача идёт без блокировки; для синхронизации это безопасно, она
идемпотентна.

Периодичность лежит в таблице `app_settings`, ключ `google_sync` — чтобы менять
её из админки, не перезапуская процесс.

Push-уведомления Google (`events.watch`) не используются: нужен публичный
HTTPS-адрес. Появится домен — добавим, опрос останется запасным путём.

## Решение 5. Мост между async-ботом и sync-базой

Хендлеры aiogram асинхронные, а SQLAlchemy и все сервисы — синхронные.
`app/bot/db.py` сводит их так:

```python
async def run_db(fn, *args, **kwargs):
    def call():
        db = SessionLocal()
        try:
            return fn(db, *args, **kwargs)
        finally:
            db.close()
    return await asyncio.to_thread(call)
```

Сессия живёт внутри потока и там же закрывается. Поэтому `app/bot/services.py`
возвращает **словари, а не ORM-объекты**: после закрытия сессии объект отдаёт
`DetachedInstanceError` при первом же обращении к полю. Это не стилистика — это
условие работоспособности.

## Слои и каталоги

| Каталог | Ответственность |
|---|---|
| `app/models/` | Таблицы. Бизнес-логики нет |
| `app/services/` | Бизнес-логика: расписание, брони, календарь, аудит, настройки |
| `app/services/booking_flow.py` | Единая точка записи — см. решение 2 |
| `app/integrations/google/` | OAuth и Calendar API. Знают про Google, не знают про брони |
| `app/api/routes/` | Вход и OAuth-callback |
| `admin/routes/` | Страницы админки. Тонкие: собрать данные, отрисовать |
| `app/bot/` | Telegram: хендлеры, клавиатуры, тексты, слой данных |
| `app/scheduler.py` | Фоновые задачи |
| `app/config/` | Настройки, безопасность, сетевые обходы |

Правило зависимостей: `admin/` и `app/bot/` зависят от `app/services/`, обратно —
никогда. Сервисы не знают, кто их вызвал.

### Тексты бота вынесены

Все строки, которые видит клиент, лежат в `app/bot/texts.py`. Заказчик правит
формулировки, не читая хендлеры, — и не может при этом сломать логику.

## Таблицы

| Таблица | Назначение |
|---|---|
| `users` | Сотрудники админки: логин, пароль, роль, отдельные права |
| `employees` | Специалисты, к которым записываются |
| `services` | Услуги и их длительность |
| `clients` | Клиенты, включая `telegram_id` |
| `schedules` | Рабочие дни, часы и перерыв |
| `bookings` | Записи. `google_event_id` — связь с событием |
| `google_accounts` | Подключённые аккаунты, refresh-токен шифрованный |
| `calendars` | Календари аккаунта, `sync_token` для инкрементальной синхронизации |
| `notifications` | Отправленные уведомления; уникальная пара (booking_id, kind) |
| `app_settings` | Настройки, меняемые из админки |
| `audit_logs` | Кто, что и когда изменил |

`sync_token` лежит на календаре, а не на аккаунте: токен относится к конкретному
календарю, и общий на аккаунт превращал бы каждый прогон в полную
пересинхронизацию — Google отвечал бы кодом 410.

## Сетевые обходы

`app/config/network.py` ставит IPv4 раньше IPv6 в `socket.getaddrinfo`. Причина
конкретная: на машине разработки DNS отдаёт восемь IPv6-адресов Google перед
IPv4, а IPv6-маршрут не отвечает — `httplib2` (транспорт
google-api-python-client) упирается в таймаут. Замер: IPv4 — 0.06 с, IPv6 —
таймаут 6 с.

Отключается через `PREFER_IPV4=false`, если хост заведомо ходит по IPv6.

На `aiohttp`, то есть на бота, патч не влияет: он резолвит через
`aiohappyeyeballs` мимо `socket.getaddrinfo` и справляется сам. Попытка
принудительно ограничить его семейством `AF_INET` делала **хуже** — 21 секунда
против 0.09–0.71 с у обычной сессии. Не повторять.

## Тесты

```bash
.venv\Scripts\python -m pytest tests -q
```

84 теста. Отдельная база `booking_test` создаётся автоматически, таблицы
чистятся между тестами — рабочие данные не трогаются.

Интеграционный тест бота (`tests/integration/test_bot_flow.py`) прогоняет
настоящие апдейты через настоящий диспетчер, подменив только транспорт: сессия
записывает вызовы вместо отправки в Telegram. Проверяются тексты и кнопки — то,
что увидит клиент.

Две ловушки, на которые уже наступали:

- `run_db` открывает сессию сам, мимо тестового движка. Без autouse-фикстуры,
  подменяющей `app.bot.db.SessionLocal`, тест пишет в рабочую базу и дёргает
  живой Google.
- Роутеры aiogram — модульные синглтоны. Второй `Dispatcher` в том же прогоне
  даёт `RuntimeError: Router is already attached`, поэтому диспетчер — одна
  фикстура на модуль.
